# Projections, Generators, and Analyzers

## Projection principle

A projection deterministically derives a view or artifact from a project revision. It does not become an independent authority.

Projection inputs:

- immutable project revision,
- selected scope,
- purpose or profile,
- generator version,
- options,
- extension registry versions.

Projection outputs:

- content,
- media type,
- source element map,
- warnings,
- content hash,
- generator metadata,
- reproducibility metadata.

## Projection families

### Interactive lenses
Story, flow, state, interface, system, evidence, and slice views.

### Documentation
Narrative specifications, user guides, architecture reports, review packets.

### Behavioral specifications
TinyBDD-style C# skeletons, Gherkin-like text, example tables, transition tables.

### Contracts
OpenAPI fragments, JSON schemas, message catalogs, MCP definitions, CLI command specifications.

### Implementation plans
Vertical-slice packets, module maps, port and adapter outlines, data migration plans.

### Code scaffolding
C# projects, records, commands, results, handlers, ports, tests, serializers, and registration.

### Validation
Rule reports, traceability matrices, evidence matrices, impact reports.

## Generator contract

```csharp
public interface IProjectProjectionGenerator
{
    ProjectionKind Kind { get; }
    ProjectionGeneratorVersion Version { get; }

    ValueTask<ProjectionPlan> PlanAsync(
        ProjectSnapshot snapshot,
        ProjectionRequest request,
        CancellationToken cancellationToken);

    ValueTask<ProjectionArtifact> GenerateAsync(
        ProjectSnapshot snapshot,
        ProjectionPlan plan,
        CancellationToken cancellationToken);
}
```

`PlanAsync` identifies missing prerequisites before expensive work.

## Determinism

A projection is deterministic when the same canonical snapshot, generator version, registry versions, and options produce the same canonical output bytes.

Avoid:

- current time in content unless passed as an explicit option,
- random identifier generation,
- machine paths,
- unordered reflection enumeration,
- environment-dependent line endings,
- live provider calls during generation,
- hidden mutable templates.

## Provenance

Generated files include:

```text
Generated by: Project Builder C# Slice Generator 1.2.0
Project: <id>
Revision: 42
Scope: <element id>
Model hash: <sha256>
Generated at: informational, excluded from canonical hash if necessary
Source elements:
  PB:<id>
  PB:<id>
```

Source maps can be sidecar JSON when comments would pollute code.

## C# generation strategy

### Generate definitions, not opaque applications

Good candidates:

- strongly typed identifiers and value records,
- closed result hierarchies,
- command and event records,
- serialization contexts,
- registry declarations,
- exhaustive visitors,
- test case data,
- API contract types,
- project file schemas,
- scaffolding with explicit TODO gaps.

Poor candidates:

- hidden business logic no human can inspect,
- provider calls inferred without decision,
- reflection-heavy runtime magic,
- code that must be hand-edited inside generated regions,
- architecture selected from a vague scenario.

### Partial types

Use partial types when:

- generated and authored responsibilities are clearly distinct,
- generated member names are stable,
- the authored part does not depend on generated implementation quirks,
- diagnostics explain collisions.

### Standalone generated project

Use a generated project when the output is intended as a starting scaffold or external artifact. It carries its own manifest and model provenance.

## Source generators

Roslyn incremental generators can produce:

- meta-model registries,
- exhaustive mappings for element kinds,
- JSON serialization contexts,
- validators from declarative descriptors,
- strongly typed relation builders,
- stable command catalogs,
- lens descriptor tables.

Generator design requirements:

- incremental and deterministic,
- no network or filesystem discovery outside AdditionalFiles,
- minimal dependencies,
- metadata-only analysis where feasible,
- readable generated C#,
- stable ordering,
- diagnostics with locations,
- no runtime generator dependency leakage,
- performance benchmarks for large registries.

## Analyzers

Analyzers can enforce:

- Domain references no infrastructure namespaces.
- Domain rules do not inject clocks or clients directly.
- Result unions are exhaustively handled at presentation boundaries.
- Generated model identifiers are used in implementation annotations correctly.
- Provider DTOs do not cross adapter boundaries.
- Commands include required operation identity where policy says so.
- public APIs have explicit contracts.
- model-linked tests reference valid identifiers.
- reflection or dynamic code use is reviewed.
- generated files are not edited.

## Code fixes

A code fix should teach the architecture.

Examples:

- Move provider type behind an Application port.
- Add missing semantic result case.
- Add model-reference attribute.
- replace a primitive parameter with generated value type.
- add cancellation token propagation.
- add explicit mapping from presentation state to intent.

Do not offer code fixes that mechanically hide the finding.

## Model-to-code references

Possible explicit attribute:

```csharp
[ModelElement("0191...")]
public sealed record AddScannedValue(...);
```

The analyzer validates:

- identifier format,
- element kind compatibility,
- duplicate binding policy,
- source model or exported manifest,
- baseline or revision where needed.

An alternative manifest avoids embedding identifiers in production assemblies. The decision is made after a spike.

## Round trip

Round trip is supported only for well-defined areas:

- adding implementation reference from code annotation,
- ingesting test result for a linked claim,
- recognizing generated scaffold completion markers,
- importing contract changes as candidate model diffs.

Handwritten code is not parsed into authoritative domain behavior automatically. Reverse modeling creates proposals and gaps.

## Plugin projections

External generators execute:

- out of process,
- in a sandbox or constrained worker,
- against an immutable exported snapshot,
- with declared permissions,
- with time and resource limits,
- with signed package and compatibility metadata where policy requires.

They return artifacts and diagnostics, not direct database mutations.

## Testing generators

Evidence includes:

- snapshot tests,
- compile tests,
- behavior tests of generated code,
- deterministic hash tests,
- incremental-update tests,
- diagnostics tests,
- malicious or malformed model tests,
- performance tests,
- compatibility fixtures.

Snapshot approval alone is insufficient because visually plausible generated code can be semantically wrong.

## Projection lifecycle

Statuses:

- requested,
- planning,
- blocked by findings,
- queued,
- running,
- succeeded,
- failed,
- cancelled,
- stale,
- superseded.

A projection becomes stale when model scope or generator inputs change.

## Template governance

Templates are versioned, reviewed artifacts. They cannot execute arbitrary code. A template declares:

- compatible generator,
- inputs,
- model assumptions,
- output files,
- escaping and safety behavior,
- license metadata,
- version.

Template changes can alter output without changing the canonical project format, so projection versions remain explicit.
